# doc-verify

**제출 전에 틀린 걸 찾는다.** 숫자가 최우선이고, 그다음이 근거 자료와의 대조다.

이 스킬이 생긴 이유 — 제출한 견적서의 금액이 틀린 사고가 있었다. 숫자는 되돌릴 수 없다.

## 원칙

1. **숫자는 스크립트가 다시 더한다.** LLM이 눈으로 검산하지 않는다. 계산은 `verify.py`가 하고, 결과만 읽는다.
2. **추측하지 않는다.** 어느 합산 가설과도 안 맞으면 그럴듯한 답을 만들지 말고 FAIL로 올린다. 못 읽은 파일(스캔 PDF 등)은 **못 읽었다고 리포트에 쓴다** — 조용히 빠뜨리면 "다 봤다"로 읽힌다.
3. **판단은 사용자가 한다.** 보수적으로 전부 surface 하고, 고칠지 말지는 예준님이 정한다.
4. **원본을 고치지 않는다.** 검증만 한다. 수정은 사용자가 하거나, 별도로 지시받았을 때만.

## 절차

### 1. 대상과 범위를 정한다
- 파일 하나를 받으면 **그 파일이 든 폴더**가 기본 컨텍스트다.
- 폴더를 받으면 그 안의 제출 예정 파일(최신 날짜·`clean`/`final`/`제출`/`submission` 류 이름)을 대상으로 잡고, 애매하면 묻는다.
- **baseline(이전 계약·원본 rev)이 그 폴더에 없는 경우가 많다.** 없으면 `--project`로 상위 프로젝트 폴더의 형제 폴더까지 넓힌다.
  - 실제 사례: `260731_NDA 수정본 및 사인 준비`에는 최종본과 메일뿐이었고, 대조 기준이 된 P2H 원본은 형제 폴더 `260508_NDA 준비`에 있었다.

### 2. 숫자 검증 (결정론) — 가장 먼저, 반드시
```
python <skill>/scripts/verify.py numbers "<대상파일>" --json "<scratch>/f.json"
```
잡는 것:
- **합계·소계** — '합계/総計/Total/Sub Total' 행을 찾아 위쪽 숫자와 대조. 빈 행·시트 중간 헤더·2단 중첩 소계를 감안해 여러 합산 가설(바로 위 블록 / 항목 전체 / 소계 합 / 소계+미포함 항목)을 세우고 맞는 것을 찾는다. 하나도 안 맞으면 FAIL.
- **행 산술** — 단가 × 수량 = 금액 (블록별 헤더 기준)
- **엑셀 수식** — 합계 셀이 손입력이면 CHECK, `=SUM(범위)`는 실제로 다시 더해 캐시값과 대조
- **백분율** — % 열 합 100, 본문 결제조건 %(20/70/10) 합산
- **숫자오염** — 날짜 문맥의 이상한 연도, 글자·숫자가 붙어버린 토큰 (편집 중 붙여넣기 사고)
- **표기** — `three 3` 같은 괄호 누락·글자↔숫자 불일치, 천단위 콤마 혼재, 통화 혼재
- **개정흔적** — track changes 삽입/삭제, 코멘트 잔존 (제출 사고 1순위)
- **자리표시자** — `{{마커}}`, TBD, XXX 잔존

> **표를 못 찾거나 결과가 0건이면 `extract.py <파일>`로 추출 결과를 눈으로 먼저 확인**한다. 레이아웃이 특이해 파싱이 안 된 것일 수 있고, 그때는 "검산 못 했다"고 리포트해야 한다.

> **시트가 많은 파일은 반드시 시트를 좁힌다.** 見積計算書まとめ 같은 20시트 이상 내부 계산서는 시트 간 수식이 얽혀 있어 전체 실행 시 지적이 수십 건 나온다(대부분 검산 불가지 오류가 아님). 없는 시트명을 주면 시트 목록을 출력하니 그걸로 고른다.
> ```
> python <skill>/scripts/verify.py numbers "<파일>" --sheet "見積計算書（まとめ）"
> ```
> 실측: 전체 실행 FAIL 77건 → 제출 대상 시트 1개로 좁히면 FAIL 1건(코멘트 잔존 — 진짜 지적).

> **숫자오염·표기 검사는 문장에만 적용된다.** 표 셀의 품번·도번(`R10301`, `1315C780`, `US20250001477A1`)은 정상이므로 제외한다. 붙여넣기 사고는 문장에서 일어난다.

### 3. 폴더 자료 대조 (컨텍스트)
```
python <skill>/scripts/verify.py crossref "<폴더>" --target "<대상파일명>" [--project] [--min 1000]
```
- 폴더(또는 프로젝트) 안 모든 xlsx/xls/pdf/docx/pptx/**msg**에서 숫자를 뽑아 **값 → 출처** 인덱스를 만든다. 전화·주소·참조번호는 '식별자'로 분류해 숨긴다(`--all`로 표시).
- **2개 이상 파일에 공통으로 나오는 숫자** = 대조 기준값 후보. **대상에만 있는 숫자** = 근거 없는 값 후보.
- 스캔 PDF는 `scanned`로 따로 보고된다 → **PNG로 변환해 Read 도구로 직접 읽는다**:
  ```
  python <skill>/../payment-log/scripts/pdf_to_png.py "<x.pdf>" "<scratch>/png" 170
  ```

**여기서부터는 스크립트가 아니라 Claude가 읽고 판단한다.** crossref는 후보만 준다. 실제로 해야 할 일:
- 메일 스레드를 읽어 **합의된 값·조건**을 뽑고 대상 문서와 맞는지 본다.
- 이전 rev / 원계약(baseline)과 대조해 **무엇이 바뀌었고 왜 바뀌었는지** 확인한다.
- 회의록·내부 노트의 **내부 결정과 최종본이 어긋나는지** 본다.
- 옵시디언 볼트에 프로젝트 노트가 있으면 참조한다(경로 규칙은 `steel-project-wiki-context`).

### 4. HTML 리포트
스크립트 findings + Claude가 대조로 찾은 findings를 **하나의 JSON으로 합쳐** 리포트를 만든다.
```
python <skill>/scripts/report.py "<input.json>" "<소스폴더>/<날짜>_검증 리포트.html"
```
- 입력 스키마는 `report.py` 상단 docstring 참조. 각 finding에 `"source": "script" | "context"`를 반드시 넣어 **자동 검산과 판단을 구분**한다.
- `context_files`(같이 읽은 자료)와 `unreadable`(못 읽은 자료)을 반드시 채운다 — 검증 범위를 드러내는 것이 이 리포트의 핵심이다.
- `checked`에 **통과한 검산**도 넣는다. 무엇을 실제로 봤는지 보여야 신뢰할 수 있다.
- HTML은 **소스 폴더(U:\)에 저장**한다(볼트 아님). Primetals 브랜드·한국어 고정 — `primetals-text-style` 규격을 `report.py`가 내장하고 있다.

### 5. 보고
채팅으로 **FAIL부터** 요약한다. 고칠 값이 확정된 것은 정확한 수정값까지 준다(예: `2015-0115...` → `2015-01-12`).

## 심각도

| | 뜻 | 처리 |
|---|---|---|
| **FAIL** | 계산이 안 맞거나 확정된 결함 | 제출 전 반드시 수정 |
| **CHECK** | 사람이 봐야 하는 것 | 의도 확인 후 판단 |
| **INFO** | 참고 | 필요시만 |
| **OK** | 검산 통과 | 무엇을 봤는지 보여주는 근거 |

## 용도별 강조점

- **고객사 제출** — 숫자, 이전 건 텍스트·금액 잔존, 변경이력·코멘트 잔존, 필수항목(견적일·유효기한·서명란), 통화·납기·결제조건
- **PTJ 내부승인** — 숫자, 근거자료(見積計算書·메이커 견적)와의 정합, 계약 기준선 대비 증감, 내부 결정과 최종안의 불일치
- **사내 보고** — 숫자, 이전 보고와의 일관성, 회의록·메일 근거와 결론의 정합

## 한계 (알고 쓸 것)

- **스캔 PDF는 자동 검산 불가.** PNG로 바꿔 직접 읽어야 하고, 그 사실을 리포트에 남긴다.
- **시트 간 수식이 얽힌 내부 계산서는 전체 검산이 안 된다.** `--sheet`로 좁혀 쓴다.
- 병합셀이 심한 시트는 표 인식이 어긋날 수 있다 → `extract.py`로 확인.
- crossref는 **후보만** 준다. 같은 숫자가 우연히 겹치거나, 다른 숫자가 실은 같은 항목일 수 있다.
- 문장 속 논리·법적 판단은 검증 대상이 아니다.
