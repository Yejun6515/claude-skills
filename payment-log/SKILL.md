# payment-log

**入金連絡 메일 1건 → 볼트 수금 기록**을 결정론적으로 처리한다. 판단·번역이 필요한 메일은 `mail-bridge` 소관이고, 이 스킬은 **정형 표를 읽어 숫자를 대조·기록**하는 일만 한다.

Vault 루트: `%USERPROFILE%\.claude\skills\_config\local-paths.md`의 `vault_root:`.

## 왜 별도 스킬인가
入金連絡은 서식이 고정(入金内訳一覧表)이고, 결과물도 고정(입금 노트 1장 + 개요 §4.3 갱신)이다. 대신 **본문이 비어 있고 데이터가 전부 첨부 이미지 안**이라 전용 추출 경로가 필요하다. 또 입금은 "이벤트"가 아니라 **잔액이 있는 상태값**이라, 활동 테이블(§4.2)이 아니라 누계·미수를 갖는 §4.3에 쌓아야 한다.

## 절차

### 1. 메일에서 데이터 추출
```
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\extract_msg_attachments.ps1 `
  -MsgPath "<入金連絡...msg>" -OutDir "<scratchpad>\msg"
```
- 본문은 대개 한 줄(「下記のとおり入金がありましたので…」) — **의미 있는 데이터 없음**.
- 저장된 `image001.png`(入金内訳一覧表)을 **Read 도구로 직접 본다**. OCR 도구 불필요.
- 표에서 뽑을 값: `入金番号` · `入金日`(+Ad-hoc 여부) · `経理提出期限` · `取引先名`/`取引先CD` · `入金額(円貨/外貨)` · `請求書番号` · `WBS element` · `控除` · `合計` · `備考`.
- 여러 행(복수 청구서 합산 입금)일 수 있다 — **모든 행을 잡고 合計와 맞는지 검산**한다.

### 2. 프로젝트 특정 (되묻지 않는다)
- **WBS element가 조인 키**다. `E.1024P531.B` → 오더코드 `1024P531`.
- 개요 노트 §1.2 `PTJ Menu Order Code`, §4.3 계약 기준선의 PO No.와 대조해 프로젝트를 찾는다.
- 볼트 전체 Grep 금지 — 메일/폴더 경로의 회사·프로젝트로 해당 폴더에 직행한 뒤, 확신 없을 때만 오더코드로 좁혀 검색한다.
- 매칭 실패 시에만 사용자에게 묻는다.

### 3. 계약 기준선 확보 (없으면 1회만)
개요 노트 §4.3에 **계약 기준선**이 이미 있으면 그대로 쓴다. 없으면 PO에서 뽑아 고정한다.
- PO 원본은 보통 프로젝트 소스 폴더의 `*_PO.pdf`(예: `PTJ menu 자료\T_EP531_0004_PO.pdf`).
- **PTKR PO는 스캔 이미지 PDF** — 텍스트 추출이 0자다. 아래로 PNG 변환 후 **Read 도구로 읽는다**.
```
C:\Users\Z006K14G\tv\Scripts\python.exe scripts\pdf_to_png.py "<PO.pdf>" "<scratchpad>\PO" 180
```
- 기록할 항목: **PO No. · 계약일 · 총액(통화, excl. tax) · 품목별 금액 · Incoterms · WBS/Order code · Payment Terms 전문**.
- Payment Terms를 **마일스톤 표로 전개**한다(조건 × 금액). PTKR 표준 패턴 예:
  - 기자재: 20% 계약 후 30일 / 70% B/L(FOB) 후 30일 / 10% FAC(또는 Deemed FAC) 후 30일
  - 감독서비스: 100% 소비 완료일 또는 FAC 중 빠른 쪽 +30일
- **감독서비스는 기자재와 별도 조건**이다 — 합쳐서 %를 계산하지 않는다.

### 4. 마일스톤 대조 (이 스킬의 핵심 가치)
입금액을 **품목 금액 × 조건 %** 조합과 맞춰 어느 마일스톤인지 판정한다.
- 단일 %가 아니라 **합산(20%+70%=90%)일 수 있다** — 실제 사례: K2H 86,746,920 × 90% = 78,072,228 정확히 일치.
- 정확히 떨어지면 마일스톤 확정, 안 떨어지면 **추정하지 말고 "미분류"로 두고 flag**한다.
- 검산: 누계 = 이전 누계 + 이번 입금, 미수 = 계약총액 − 누계.

### 5. 산출물
**(a) 입금 이벤트 노트** — 프로젝트 폴더에 `YYMMDD_<라인> 입금연락.md`

> ⚠️ **먼저 중복을 확인한다.** 같은 입금 건의 노트가 이미 있을 수 있다(파일명이 `입금연락`이 아니라 `현대제철 AP 10%입금`처럼 다를 수 있으므로 **날짜·금액·請求書番号으로 확인**). 있으면 **새로 만들지 말고 기존 노트에 payment frontmatter(Amount/Currency/Invoice/WBS/PO/Payer)와 `Category: payment`를 보강**하고 `## 계약 대비`만 덧붙인다. 개요 §4.2에 이미 빌링 행이 있으면 그 행도 마일스톤 판정으로 갱신한다(행 신설 금지). — 2026-07-29 실제로 중복 생성 사고가 있었음.
```yaml
---
Date: YYYY-MM-DD          # 入金日
Category:
  - payment
mentions:
Google Drive:
description: "<영어 한 문단 — 금액·통화·지급주체·청구서·WBS·마일스톤·미수>"
tags:
  - topic/payment
Amount: 78072228          # 숫자만(콤마·통화기호 없이) — Base 집계용
Currency: JPY
Invoice: "4012241"        # 따옴표 필수(선행 0 보존)
WBS: E.1024P531.B
PO: "4600003845"
Payer: Primetals Technologies Korea
---
```
본문: `## Event`(소스 폴더 `file:///` 링크) → `## 핵심요약` → `## 계약 대비`(마일스톤 판정·누계·미수·확인 필요 사항) → `## 관련 위키`.

**(b) 개요 노트 §4.3 갱신** — 입금 이력 표에 1행(최신순 맨 위), 마일스톤 표 상태 갱신(⬜ 미수 → ✅ 입금일), **미수 잔액 줄 재계산**.

**(c) 리포트** — 프로젝트 / 이번 입금 / 누계·계약대비% / 미수 잔액과 그 조건 / flag 항목.

### 6. 반드시 flag할 것 (보수적으로 surface, 판단은 사용자)
- 입금액이 어떤 마일스톤 조합과도 안 맞음
- 같은 `請求書番号`이 이미 기록됨(중복 입금 의심)
- `控除`(공제)가 0이 아님
- 누계가 계약총액 초과
- **조건 대비 지연** — 예: 선급 20%가 계약 후 30일 조건인데 실제 입금이 1년 이상 뒤. 지연 여부를 단정하지 말고 "별도 청구가 있었는지 확인 권장"으로 올린다.
- 通貨가 계약통화와 다름(円貨/外貨 칸 확인)

## 제약
- **숫자를 지어내지 않는다.** 이미지에서 못 읽은 칸은 공란으로 두고 보고한다.
- 개요 노트의 다른 절(§1·§2·§3·§5)과 `# Yejun's memo`는 건드리지 않는다.
- §4.2 활동 테이블에 입금 행을 중복 추가하지 않는다(출하·invoice 발행 등 빌링 *이벤트*만 §4.2, 수금은 §4.3).
- BOM 없는 UTF-8, 날짜 `YYYY-MM-DD`, 금액은 표에서 3자리 콤마·frontmatter에서는 숫자만.
- 전 프로젝트 횡단 현황은 `{vault}\01. Projects\0_payment.base`가 `Category: payment` 노트를 모아 보여준다 — 새 프로퍼티를 임의로 늘리면 뷰가 깨지니 위 frontmatter 키를 지킨다.
- 계약 기준선 추출은 PO 1회로 끝 — 이후 입금은 기준선 대조만 한다. 계약 변경(Amendment/Change order) 발견 시 기준선을 갱신하고 그 사실을 리포트한다.
